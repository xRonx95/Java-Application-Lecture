Learning Objectives

  • explain why object data should be protected;
  • identify the purpose of access modifiers;

  • test valid, invalid, and boundary inputs; and
  • design a complete encapsulated Java class.
02

Core Concept

What is encapsulation?

Encapsulation is the practice of keeping an object's data and the methods that work on that data together inside one class, while limiting direct access to the object's internal details.

In simple words, encapsulation protects data. Instead of allowing any part of a program to change a value directly, the class provides controlled methods for reading or updating it.

🏧

Real-world analogy: an ATM

You cannot directly touch the money or edit the balance stored in a bank's system. You use approved actions such as deposit, withdraw, and check balance. The ATM hides complex internal operations and allows only valid requests.

1

Bundle

Place related data and behavior inside one class.

2

Hide

Make sensitive fields private so outside code cannot directly edit them.

3

Control

Provide methods that decide how data may be read or changed.

03

Process

How does encapsulation work?

Step 1

Declare fields as private

Private fields are accessible only inside their own class.

Step 2

Provide public methods

Getters, setters, and action methods become the safe entry points.

Step 3

Check incoming values

Methods reject invalid data before it reaches the private field.

Student.javaBasic example
public class Student {
    // Private data cannot be changed directly outside this class.
    private String name;
    private int age;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        if (name != null && !name.isBlank()) {
            this.name = name;
        }
    }

    public int getAge() {
        return age;
    }

    public void setAge(int age) {
        if (age >= 5 && age <= 100) {
            this.age = age;
        }
    }
}
Explain it this way: The fields are locked. The methods are guarded doors. Each guard checks whether a request is allowed.

Access Control

Java access modifiers

Access modifiers determine where a class member can be used. Good encapsulation normally keeps fields private and exposes only the methods that other classes need.

ModifierSame classSame packageSubclassEverywhereTypical use
privateYesNoNoNoProtect internal fields
defaultYesYesOnly in packageNoPackage-level helpers
protectedYesYesYesNoControlled inheritance
publicYesYesYesYesClass interface or API

Important: Making every field public breaks encapsulation because any code can assign an invalid value without permission.

05

Controlled Access

Getters, setters, and behavior methods

Getter (accessor)

A getter returns a value without giving direct access to the field itself.

public String getName() {
  return name;
}

Setter (mutator)

A setter changes a value and can validate it first.

public void setName(String name) {
  this.name = name;
}

Not every field needs both methods

Encapsulation does not mean automatically creating a getter and setter for everything. Give only the access the program actually needs:

  • Read-only: provide a getter but no setter.
  • Write-only: provide a method that accepts a value but does not reveal it, such as a password method.
  • Behavior-based: use meaningful actions such as deposit() and withdraw() instead of setBalance().
06

Protecting State

Validation and class invariants

An invariant is a rule that must always remain true for an object. For a bank account, one rule might be: “A deposit must be greater than zero.” Encapsulated methods enforce that rule.

BankAccount.javaBehavior-based design
public class BankAccount {
    private double balance;

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException(
                "Deposit must be greater than zero."
            );
        }
        balance += amount;
    }

    public boolean withdraw(double amount) {
        if (amount <= 0 || amount > balance) {
            return false;
        }
        balance -= amount;
        return true;
    }
}

Why this is safer: Outside code can request a withdrawal, but only the BankAccount class decides whether the request is valid.

07

Valid From the Start

Constructor validation

A constructor creates an object. If required values are checked in the constructor, the program cannot create an object that starts in an invalid state.

Receive values

The constructor receives the student's name and age.

Check rules

Name must not be blank; age must be reasonable.

Reject invalid data

Throw an exception with a clear message.

Create a valid object

Assign fields only after all rules pass.

Student.javaConstructor validation
public class Student {
    private final String studentId;
    private String name;
    private int age;

    public Student(String studentId, String name, int age) {
        if (studentId == null || studentId.isBlank()) {
            throw new IllegalArgumentException("Student ID is required.");
        }
        this.studentId = studentId;
        setName(name);   // Reuse the validation in the setter.
        setAge(age);
    }
}

08

Handling Invalid Requests

Reject, return, or throw?

When a request is invalid, a method should communicate the result clearly. Three common choices are shown below.

TechniqueBest used whenExample
Return booleanFailure is expected and the caller can try again.withdraw() returns false.
Throw an exceptionThe caller has broken a required rule.A negative deposit throws IllegalArgumentException.
Return a result objectThe caller needs a status plus a detailed message.EnrollmentResult contains success and reason.

Avoid silent failure: If an invalid value is ignored with no message or result, students may not know why the object did not change.

Quick decision

Which response would you choose?

A student tries to enroll in a class that is already full. Discuss whether the method should return false, throw an exception, or return a result object with the message “Class is full.”

Advanced Topic

Encapsulation and immutable objects

An immutable object's state cannot change after it is created. Immutability is a strong form of encapsulation because changes are prevented instead of merely controlled.

SchoolId.javaImmutable class
public final class SchoolId {
    private final String value;

    public SchoolId(String value) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("ID is required.");
        }
        this.value = value;
    }

    public String getValue() {
        return value;
    }
}
  • The class is final, so it cannot be extended.
  • The field is private final, so it is assigned only once.
  • Validation happens in the constructor.
  • There is no setter.
10

Protecting Lists and Arrays

Defensive copies

Private does not fully protect a list if a getter returns the original mutable list. Outside code would receive a reference to the same object and could change its contents.

Unsafe: returns the original 
public List<String> getSubjects() {
  return subjects;
}
Safer: returns a copy 
public List<String> getSubjects() {
  return List.copyOf(subjects);
}

Testing an encapsulated class

Good tests check both valid and invalid paths. For every rule, write at least one test that should pass and one that should fail.

Related Ideas

Encapsulation, abstraction, and data hiding

ConceptMain questionMeaningExample
EncapsulationHow is access controlled?Bundles data and methods while controlling access.A private balance changed through deposit().
Data hidingWhat should be protected?Prevents direct access to internal details.The balance field is private.
AbstractionWhat should the user see?Shows essential operations and hides complexity.A user selects “Withdraw” without knowing bank-server logic.

These ideas work together. Data hiding supports encapsulation, and encapsulation helps a class present a simple abstraction.

13

Why It Matters

Benefits of encapsulation

Data protection

Invalid or unsafe values can be rejected.

Maintainability

Internal code may change without affecting its users.

Debugging

Changes pass through known methods, making errors easier to trace.

Reusability

A well-designed class can be safely used in other programs.

Flexibility

The internal representation can change while the public interface stays the same.

Clear responsibility

Each class manages and protects its own state.

14

Avoid These

Common mistakes

Public fields

Any part of the program can put the object into an invalid state.

Setters without validation

A setter that accepts every value gives little protection.

Returning a mutable collection

Returning the original list lets outside code change internal data. Return an unmodifiable view or a copy.

Too many responsibilities

Encapsulation does not fix a class that tries to do everything. Keep each class focused.

Not encapsulated 
class Student {
  public int grade;
}

student.grade = -20;
Encapsulated 
class Student {
  private int grade;

  public void setGrade(int grade) {
    if (grade >= 0 && grade <= 100) {
      this.grade = grade;
    }
  }
}

Follow Along

Guided mini-project: LibraryBook

Build a small class one step at a time. Complete and run each step before moving to the next one.

Step 1 · Create the shell

Add the class and private fields

public class LibraryBook {
  private final String title;
  private String borrower;
  private boolean available;
}

Check: Code outside the class should not be able to write to these fields directly.

Step 2 · Build a valid object

Add a constructor

public LibraryBook(String title) {
  if (title == null || title.isBlank())
    throw new IllegalArgumentException("Title is required.");
  this.title = title;
  this.available = true;
}

Check: Try creating a book with "". The constructor should reject it.

Step 3 · Add safe behavior

Create the borrow method

public boolean borrowBook(String studentName) {
  if (!available || studentName == null || studentName.isBlank())
    return false;
  borrower = studentName;
  available = false;
  return true;
}

Check: The first valid borrower succeeds. A second borrower should fail while the book is unavailable.

Step 4 · Restore the state

Create the return method

public void returnBook() {
  borrower = null;
  available = true;
}

Check: After returning the book, another student should be able to borrow it.

Step 5 · Expose only what is needed

Add read-only getters

public String getTitle() { return title; }
public String getBorrower() { return borrower; }
public boolean isAvailable() { return available; }

Check: There is no setAvailable(). Availability changes only when the book is borrowed or returned.

Show the complete LibraryBook class 
public class LibraryBook {
    private final String title;
    private String borrower;
    private boolean available;

    public LibraryBook(String title) {
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("Title is required.");
        }
        this.title = title;
        available = true;
    }

    public boolean borrowBook(String studentName) {
        if (!available || studentName == null || studentName.isBlank()) {
            return false;
        }
        borrower = studentName;
        available = false;
        return true;
    }

    public void returnBook() {
        borrower = null;
        available = true;
    }

    public String getTitle() { return title; }
    public String getBorrower() { return borrower; }
    public boolean isAvailable() { return available; }
}

Practice

Learning activities

Activity 1 · Identify

Find the problem

A class has these public fields: username, password, and age. Explain two risks and suggest how to protect the fields.

Activity 2 · Code

Create a Product class

  1. Create private fields for name, price, and stock.
  2. Do not allow an empty product name.
  3. Do not allow a negative price or stock value.
  4. Add sell(int quantity) and prevent selling more than the available stock.
  5. Add getters for all three fields.
Activity 3 · Discuss

Think–pair–share

Why is withdraw(amount) usually better than setBalance(amount)? Give one example in which a setter would allow an impossible or unsafe state.

Show a possible answer for Activity 2 
public class Product {
    private String name;
    private double price;
    private int stock;

    public Product(String name, double price, int stock) {
        setName(name);
        setPrice(price);
        setStock(stock);
    }

    public void setName(String name) {
        if (name == null || name.isBlank())
            throw new IllegalArgumentException("Name is required.");
        this.name = name;
    }

    public void setPrice(double price) {
        if (price < 0)
            throw new IllegalArgumentException("Invalid price.");
        this.price = price;
    }

    public void setStock(int stock) {
        if (stock < 0)
            throw new IllegalArgumentException("Invalid stock.");
        this.stock = stock;
    }

    public boolean sell(int quantity) {
        if (quantity <= 0 || quantity > stock) return false;
        stock -= quantity;
        return true;
    }

    public String getName() { return name; }
    public double getPrice() { return price; }
    public int getStock() { return stock; }
}

One-minute lesson summary

Encapsulation is about giving a class responsibility for its own data. Fields are commonly kept private, while carefully designed public methods provide controlled access. Validation keeps every object in a valid state, reduces errors, and makes code safer to change.

Review Words

Glossary and final checklist

Class
A blueprint that defines an object's data and behavior.
Object
An instance of a class with its own current state.
Field
A variable stored inside an object.
State
The current values of an object's fields.
Method
A behavior or operation provided by a class.
Public interface
The public methods other code is allowed to call.
Getter
A method that reads and returns information.
Setter
A method that changes a field, often after validation.
Invariant
A rule that must remain true for every valid object.
Immutable
Unable to change state after construction.
Defensive copy
A separate copy returned to protect mutable internal data.
Boundary value
An input at the edge of an allowed range, such as 0 or 100.
